# PostgreSQL backup and restore

`npm run db:backup` creates a timestamped `pg_dump` custom archive (`-Fc -Z 9`), encrypts it with AES-256-GCM, and uploads the encrypted `.tftbak` to S3. PostgreSQL credentials are passed through environment variables, not command arguments. The script keeps local backups for `BACKUP_RETENTION_DAYS` (default 14), logs failures to `BACKUP_DIR/backup-failures.log`, and posts a generic alert to `BACKUP_ALERT_WEBHOOK_URL`. An off-server URI is mandatory except for `--local-only` outside production. Configure an S3 lifecycle retention rule separately; this script never deletes cloud objects.

Configure these private variables in the backup runner's environment: `POSTGRES_*`, `BACKUP_ENCRYPTION_KEY` (base64 encoding of 32 random bytes), `BACKUP_OFFSITE_URI=s3://bucket/prefix`, `BACKUP_ALERT_WEBHOOK_URL`, `BACKUP_RETENTION_DAYS`, and optionally `BACKUP_DIR`, `PG_DUMP_PATH`, `PG_RESTORE_PATH`, `AWS_CLI_PATH`. Match the PostgreSQL client major version to the server; for local Docker-hosted tools, `PG_TOOLS_DOCKER_IMAGE=postgres:16` and optionally `PG_TOOLS_DOCKER_HOST=host.docker.internal` run matching dump/restore clients. Use an IAM identity restricted to writing the backup prefix and an S3 bucket with access restrictions. Keep the encryption key in a separate secrets manager; losing it makes backups unusable. Do not commit credentials or the key. Restrict access to the backup directory.

The `deploy/systemd/tft-postgres-backup.{service,timer}` templates schedule the job daily at 02:00 with missed-run catch-up. Adapt installation paths and service account for the host; set `BACKUP_DIR=/var/backups/tamilfoodthaya` in the private environment file, restrict that directory to `tftbackup`, and install/enable the timer only after off-server upload and alerts have been exercised. Configure monitoring to alert if the daily job does not succeed; webhook alerts cover observed failures, not a job that never starts. On Windows, schedule `npm run db:backup` daily in Task Scheduler instead. Neither scheduler has been installed on this machine.

To verify a backup, retrieve the encrypted file from off-server storage (for example, `aws s3 cp s3://bucket/prefix/<file>.tftbak <private-backup-dir>/`). Set `RESTORE_TEST_DB` to a **new** `tft_restore_test_*` name and run:

```powershell
npm run db:restore:verify -- "C:\path\to\private-backup-dir\tft-<timestamp>.tftbak"
```

The command refuses to overwrite an existing database, decrypts to a temporary restricted file, restores into the new database, compares row counts across all 14 tables with the source, checks menu-to-category relationships, then removes the temporary plaintext archive. It leaves the restored test database for inspection. A successful local restore does **not** verify the off-server upload path or the schedule. For a production restore drill, additionally point a non-production application instance at the restored database and run API smoke tests. Never run `pg_restore --clean` against an existing database.

Local restore drill on 2026-09-27: a compressed, encrypted dump of the local development database restored into `tft_restore_test_20260927c`. All 14 tables were present; six categories and 30 menu items were restored with no orphaned menu items. A non-production application instance started against the restored database and returned HTTP 200 for health, menu items, categories, and settings. The off-server upload, daily schedule, retention cycle, and failure-alert delivery are **not verified** because no cloud destination or alert endpoint is configured.
