# Production HTTP and infrastructure contract

The intended path is Internet → HTTPS reverse proxy → built frontend and private Nest API → private PostgreSQL. `deploy/Caddyfile.example` illustrates a **host** reverse proxy only; it has not been deployed or tested with a public certificate. Caddy normally provisions HTTPS and redirects HTTP when given a real domain. Keep Nest bound to loopback or a private container network, and publish only ports 80/443 at the firewall. PostgreSQL must not have a public port. If using the separate PostgreSQL Compose service, put the backend on its internal DB network; a host-only backend cannot reach that private container.

Production startup now requires `CLIENT_URL` and `PUBLIC_API_URL` as HTTPS origins and `TRUST_PROXY_CIDRS` naming only the actual reverse proxy address/subnet. Example: `CLIENT_URL=https://food.example`, `PUBLIC_API_URL=https://food.example`, `TRUST_PROXY_CIDRS=loopback` when Caddy and Nest share a host. Nest binds to `127.0.0.1` in production by default; set `APP_BIND_HOST=0.0.0.0` only when the container/network and firewall prevent direct public access. Set `VITE_API_BASE_URL=https://food.example` when building the frontend so API calls use the same origin. The reverse proxy must replace incoming `X-Forwarded-*` headers, not trust client values; configure the exact proxy network and block direct public access to Nest. [Express documents the spoofing risk of broad proxy trust](https://expressjs.com/en/guide/behind-proxies/).

Nest rejects non-HTTPS production traffic with 426, except a loopback-only DB-backed `/api/v1/health` probe. Helmet sets CSP, HSTS, frame denial, no-sniff, and referrer headers on API responses. Production CORS accepts only `CLIENT_URL`; Swagger is disabled. JSON/form bodies are capped at 100 KB, menu uploads at 2 MB with multipart field limits. `POSTGRES_POOL_MAX` defaults to 10; shutdown hooks close the application cleanly. Production console/file logs use JSON, with file rotation at 20 MB and 14 days. Provide persistent, access-restricted log and upload storage if containerized.

Local test-database checks on 2026-09-27: direct HTTP to a public API route returned 426; a proxied HTTPS request returned 200 with HSTS, CSP, frame denial, no-sniff, and referrer headers; the exact frontend origin received CORS headers while a hostile origin did not; Swagger returned 404. Loopback health returned 200. The Caddyfile passed `caddy validate` in a disposable container. These checks do not verify a public TLS certificate or a real proxy chain.

The frontend currently includes inline startup scripts and styles, so a strict frontend CSP would break first paint. The sample Caddyfile sets baseline security headers but intentionally leaves frontend CSP enforcement pending browser testing and hash/nonce work. Do not claim frontend CSP verified. Reverse-proxy certificates, firewall rules, Caddy health, DB pool behavior under load, log collection/alerts, resource limits, and full container topology are **NOT TESTED**. Do not deploy until the backup/restore and authentication blockers are resolved and production approval is given.
